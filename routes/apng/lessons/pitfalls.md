# APNG 路线经验教训

> 从 APNG 桌宠工作流和多轮 prompt 调优中沉淀。跨角色、跨题材都适用。

---

## ⭐ 核心元教训（按重要性排序）

### 1. 参考图（reference）决定角色一致性

**现象**：每个状态的角色长得不一样，像 25 只不同的猫。

**根本原因**：没有共享参考图作锚点。

**正确做法**：
- 建立一张角色身份参考，锁定比例、配色、服装、描边和材质；
- 为不同姿势准备状态锚点，不强迫所有动作共用同一个中性姿势；
- 跨状态共享角色身份描述和已确认的视觉参考；
- 首尾帧按状态语义选择，不能因为要保持角色一致就把过渡状态错误地锚回主参考。

角色身份参考、状态锚点、共同中间帧和道具参考职责不同，详见 `routes/apng/conventions/workflow.md`。

---

### 2. 首尾帧关系决定锚定策略（3 类，不是 2 类）

**现象 a**：循环动画首尾帧不一样，循环时"咔嚓"。
**现象 b**：一次性动画结尾姿态错了（happy 完没回 idle / collapse-sleep 完反而坐起来）。
**现象 c**：过渡动画结尾停在中间姿态。

**根本原因**：把所有动画当成"循环 vs 一次性"两类处理，但实际有 **3 类**：

| 类 | loop | 首尾关系 | --last-frame 用什么 |
|---|---|---|---|
| **A. 循环** | true | 首=尾（同图） | 跟 `--image` 同一张 |
| **B. 一次性·回归型** | false | 首=尾（回原姿） | 跟 `--image` 同一张 |
| **C. 一次性·过渡型** | false | **首≠尾** | **不同的尾帧图** |

当前模板中的 C 类是状态间过渡（wake / collapse-sleep / mini-enter）。它们是状态机的桥梁；其他运行时可以有不同数量和名称。

**正确做法**：
- 使用支持 `--last-frame` / 尾帧锚定的视频模型
- A 类：`--image X --last-frame X` + prompt 强调 "Seamless loop"
- B 类：`--image X --last-frame X` + prompt 强调 "Returns to exact starting pose"（**不写 loop**，否则 AI 会做循环）
- C 类：`--image X --last-frame Y` + prompt 强调 "End pose matches {target state} EXACTLY"（**绝对不写 loop 也不写 returns to starting**）

**详细决策树 + 完整状态分类**：见 `routes/apng/conventions/loop-and-anchoring.md`。

**反面**：不支持尾帧锚定的模型更难做好循环动画和过渡动画。

---

### 3. 先判断应该重生成还是后处理

**现象**：生成视频出现问题后，要么一律重抽，要么试图用后期修复所有缺陷。

**正确做法**：按问题性质选择：

- 人体或主体结构错误、角色变形、道具换造型、错误遮挡、镜头破坏构图、核心动作未执行 → 通常重生成；
- 文字、符号、可控粒子、播放速度、可测量停顿、色键、边缘和跨片色差 → 通常后期处理；
- 多段动作只有一段失败 → 只重生成该段，保留已通过部分。

是否继续尝试由成本、授权范围和用户反馈决定，不设固定次数。

---

### 4. Prompt 的 negative 段要针对真实风险

常见翻车可以使用针对性的 negative prompt：

| 翻车现象 | Negative prompt |
|---|---|
| 尾巴 / 触角爆炸性放大 | `DO NOT inflate or balloon the {tail/antenna/etc.}` |
| 镜头平移 / 旋转 | `Camera stays completely still. DO NOT rotate or shift the camera angle.` |
| 不需要手却增生人手 | `NO hands, NO fingers, NO human body parts visible.` |
| 背景出现物体 / 阴影 | `The background must remain a uniform solid key color. No shadows, no objects, no gradients.` |
| 附属物数量变化 | 明确数量、连接关系和 `DO NOT grow additional ...` |

动作本来需要手时，不要使用 `NO hands`。改为明确哪只手、手掌朝向、手指数、肘部方向、接触点和必须保持不动的另一只手。negative 应与正向动作描述一致，避免互相冲突。

### 5. CHARACTER_PREFIX 写得越具体越好

**现象**：用 "a cute cat" 这种抽象描述，每次生成形态不同。

**正确做法**：CHARACTER_PREFIX 包含 6 个维度：
1. 物种 / 类别
2. 风格定位（chibi / kawaii / pixel-art ...）
3. 主体颜色 / 花纹
4. 主要识别特征（眼睛形状 / 耳朵 / 尾巴）
5. 描边 / 渲染风格
6. 背景要求

> CHARACTER_PREFIX 应该是一段完整角色描述，覆盖所有这些维度。一次写好，所有状态都用。

---

### 6. API 拥堵时降低并发

**现象**：外部 API 排队、限流或连续失败。

拥堵期不要在同一个失败队列里消耗时间。

**应对**：拉长批量任务间隔、降低并发、稍后重试，或按自己的服务账号替换为等价能力的模型。

---

### 7. Mini 状态由运行时构图决定

**现象**：写 mini-idle prompt 想着"就是缩小版 idle"，结果 AI 生成的 mini-idle 画面很奇怪。

**正确做法**：先检查运行时的窗口尺寸、边缘方向、裁切、hover 范围和 host 位移，再设计适合该构图的 mini 姿势。它可以是收缩姿势、贴边探头、悬浮或其他设计，没有固定体态。

运行时负责窗口和屏幕位置，素材负责角色在局部画面里的表演。不要把两种位移重复画进去。

---

### 8. 色键按角色色域选择并以成片实测为准

**现象**：色键背景与角色、头发、衣服或光效颜色重叠，或者 prompt 中的色值与输出视频实际背景不一致。

**正确做法**：选择与角色及特效色域重叠最少的 key 色，并让参考图、prompt 和抠图参数使用同一约定。抽查首尾、动作峰值和接缝附近的实际背景，不假设生成模型严格遵守输入色值。

当前 `chroma_key.py` 的硬遮罩、软边和去溢色都基于指定的 `--key-color`，支持非绿 key，也不会额外删除绿色。它不会自动估计逐帧变化的背景；需要按代表性帧调节 `--tolerance`，背景漂移明显时分段处理。详见 `routes/apng/conventions/chroma-and-edges.md`。

---

### 9. 批量生成尊重当前服务限流

**现象**：连续提交后出现排队或 429 限流。

**正确做法**：根据当前服务文档、响应头和账号限制调整并发与间隔。工具默认值只是起点，不是通用下限。提交结果不确定时先查询原任务，避免重复生成和重复扣费。

---

### 10. 成本与尝试范围

生成尝试和后期处理都会产生时间或额度成本。范围开放时可以先用一个代表性状态验证路线；用户已经要求一组状态时，按其范围执行。

用户要求生成或重试某个具体批次，就已经授权该批次。不要附加固定尝试次数，也不要在未说明的情况下扩大付费批次。

### 11. 色键背景 prompt 要禁止速度线和地面线索

**现象**：角色动作不错，但背景出现速度线、投影、地面、烟尘或光效，抠图后留下脏边。

**正确做法**：prompt 末尾显式写：

```text
Uniform solid key-color background only. No shadows, no floor, no speed lines, no motion streaks, no particles, no extra props, no camera movement.
```

对走路、爬行、跳跃这类横向动作，优先让角色做 treadmill motion：肢体在动，但身体中心基本留在画面中央。真正的窗口位移交给 host。

### 12. 抠图后要做边缘体检

**现象**：APNG 在白底看还行，放到深色桌面上出现灰边、色键溢色或半透明脏边。

**正确做法**：
- 在浅色、深色、透明棋盘三种背景下看边缘
- 灰边走 defringe / rebuild
- 色键溢色走对应 despill 或重新采样 key color
- 半透明阴影如果不是角色本体的一部分，宁可重跑视频

不要只看播放器默认背景。

预览和定稿分两档：

- 快速预览：先用工具默认档，确认动作、构图、色键背景是否值得继续；
- 定稿前：按源素材和运行时试更高质量参数，确认边缘后再压缩；
- 如果体积过大，再按目标 runtime 的限制回调 height、fps 或 colors。

不要用低清预览档直接判断最终边缘质量。

详见 `routes/apng/conventions/chroma-and-edges.md`。

### 13. 道具和第二主体需要独立身份锚点

**现象**：角色保持一致，但中途出现的道具、伙伴或云朵先是一种画风，接近尾帧时又变成另一种。

**根本原因**：角色身份参考不会自动锁定第二主体，只在尾帧出现的元素会留下大段自由发挥区。

**正确做法**：让道具在至少一个相关锚点或独立参考图中清楚可见，并在 prompt 中写明数量、轮廓、填色、描边、内部结构、接触和遮挡。从首次出现起就使用同一设计。只重生成发生漂移的片段。

### 14. 高频失真部位要逐帧检查

手势片检查手指数、手掌朝向、肘部、肩膀、接触点和固定手漂移；睡眠片检查眼睑是否意外睁开；含道具片检查数量、穿插和增生物。检查项目按动作实际结构选择，不要求不存在的身体部位。

采样帧和接触表可以定位问题，但连续播放才是最终验收。

### 15. 跨片段颜色要对齐统一基准

**现象**：每段内部颜色都稳定，拼起来仍然明显换色。

**正确做法**：选定已确认角色参考或锁定状态作为全局基准，同时检查段内漂移、片段接缝和跨状态材质。只做调色时保持 alpha、帧时长和 SVG 层不变。

## 反模式（don't）

- ❌ **不写 CHARACTER_PREFIX 直接写动作 prompt**：每次生成长得不一样
- ❌ **循环类不用尾帧锚定**：首尾姿态很容易对不齐
- ❌ **结构错误只靠后期掩盖**：人体、身份和遮挡问题通常应重生成
- ❌ **色键与角色色域冲突**：会误删主体或留下明显溢色
- ❌ **Negative 与动作要求矛盾**：需要手势却同时禁止出现手
- ❌ **忽视服务反馈连续提交**：可能排队、限流或重复扣费
- ❌ **不看运行时就设计 Mini**：姿势、裁切和位移容易互相冲突
- ❌ **把 host 位移画进 APNG**：贴边、推出、窗口移动交给运行时，APNG 只做原地表演
- ❌ **只在一种背景上看抠图结果**：透明资产必须换背景验边

## 进阶心智模型

### "尾帧锚定 + 起止文案"双保险

循环动画必做两件事：

1. **技术层**：`--last-frame` 用首帧图
2. **prompt 层**：末尾加 `Seamless loop animation. The last frame must connect perfectly back to the first frame. The character returns to the exact starting pose.`

少一层都可能翻车。

### "受控迭代"心态

AI 生成有方差。每轮记录输入、prompt 和真正改变的变量；结果已经暴露明确问题时，针对问题修改，不靠固定次数机械抽卡。用户指定继续尝试时按该范围执行，不人为设置上限。

### "按模型能力分工"

- 试 prompt 阶段：优先低成本、低并发、可接受失败的模型
- 正式生产：优先支持关键能力、输出稳定、可复现的模型

这个分工通常比单一路线更稳，也避免把所有状态绑定到一个队列或模型上。

## 跟 SVG 路线对比

| 维度 | APNG 路线（本路线） | SVG 路线 |
|---|---|---|
| 单状态时间 | 受生成队列、重试和后期影响 | 受分层和动画复杂度影响 |
| 单状态成本 | 取决于外部 API | 本地免费 |
| 微调成本 | 高（要重生） | 低（改 JS） |
| 循环无缝 | 难（要尾帧锚定 + 后期） | 完美（CSS） |
| 风格化能力 | 强（AI 啥都能生） | 弱（受限矢量化） |
| 文件大小 | 通常较大，需按运行时优化 | 通常较小，但复杂路径也会膨胀 |
| 用户技能 | prompt 工程师 | 前端 + 动画基础 |

**何时选 APNG 路线**：
- 美术能力一般，想快出成品
- 角色风格 SVG 难表达（毛茸茸、写实、复杂渐变）
- 可以接受外部 API 成本和重跑
- 不要求循环完美无缝

**何时选 SVG 路线**：
- 想要循环完美 + 文件小 + 热改
- 美术能力 OK，会写一点 JS
- 想要每个参数都可调
- 想尽量减少外部 API 成本
