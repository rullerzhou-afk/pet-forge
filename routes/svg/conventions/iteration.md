# 磨制流程：v1..vN → lock → spec

> 单个状态从"想做"到"锁定"的标准流程。

---

## 流程总览

```
[草稿]
   │
   ▼
[v1: 第一个方向]
   │
   ├─ 方向认可 ──▶ [保留评审基线，继续磨]
   │
   └─ 跑偏 ──▶ [记录原因，另存候选换方向]
                  │
                  ▼
                [v2: 新方向] → 同样的判断
                  │
                  ▼
                ... vN ...
                  │
                  ▼
              [lock]
                  │
                  ▼
              [备份 + 写 spec + 同步进度表]
```

---

## 关键概念

### 版本号服务于比较和回溯

- 新方向用清楚的名称或版本区分；尚未提交评审的小修可继续在当前实验里完成。
- 已给用户看过、已确认或需要前后对照的修复，可以另存 v2 或其他明确的修订号；保留被评审版本的快照。

不要为了维持某种编号规则覆盖已认可的基线。记录这次改的是方向、造型、动作还是缺陷，比强制区分“方向版”和“补丁版”更重要。

### 保留失败原因与重建依赖

未选方向可放在 `_archive/<state>/`，也可以留在实验目录并标明状态。保留它的用途是：

- 后续磨制可能想"绕回去看看那条路是不是真的死胡同"
- 跑偏的具体细节（哪一步翻车、为什么）是元教训源头，删了就丢了
- 人工评审 / AI 复盘时需要看历史，否则"为啥放弃这条路"无从查起

移动前检查构建脚本、素材引用和其他候选是否依赖原路径；需要搬移时同步更新引用并验证重建。归档不是锁定的必要条件，不要为整理目录破坏来源链。

### 改之前保留可恢复基线

修改已评审或已选动画前，确保能恢复用户看过的版本。可用不可变快照、带版本的备份目录或完整可重建的版本记录；要包含当时实际依赖的控制器和输入，不只留一张截图。

单文件备份示例（先确认目标名尚未使用，避免覆盖）：

```bash
cp idle-eye-follow-v1.svg.html idle-eye-follow-v1-backup-2026-05-02.svg.html
# 再另存修订候选或修改当前实验
```

理由：磨制经常"调着调着发现昨天那版本反而更好"，没备份就丢了。

## 单状态完整流程

### 第 1 步：草稿前准备（必做）

新状态开工前：

1. 看已有确认清单及相关状态，确定这次修改的基线和范围
2. 重读：
   - `routes/svg/conventions/svg-vs-canvas.md`（避免错选 Canvas）
   - `routes/svg/conventions/single-file.md`（自包含范式）
   - 需要套 preset 时才读对应预设；已有角色先保留其造型约定
3. 看公开案例或自己的历史状态里是否有类似动作

> 这一步看似繁琐，但很多跑偏都来自开工前没复查约束。

### 第 2 步：v1 起手

- 文件名：`<state>-<方向描述>-v1.svg.html`
- 从零起稿可复制 `templates/hello-idle.svg.html`，替换占位角色并保留有用的变量注释。
- 已有分层 SVG 时先核查图层、锚点、表情和控制器；从母版或已有确认动作的来源另存实验，保留造型真相源，不必重新套模板或 preset。
- 先分清请求是可保持的手动姿态、动态余动，还是完整表演；见 [rig-first.md](rig-first.md)。

### 第 3 步：按动作类型检查过程

可保持姿态检查停姿、慢拖、快拖和反向；一次性动作检查启动、全过程与目标姿态；只有声明为循环的动作才要求闭环。不为审阅方便的跳回起点自动新增回程。

对循环动作，静帧不能代替播放检查：

- 浏览器开发者工具关掉，全屏播放足够多的完整周期，至少覆盖最长的眨眼、呼吸或次级动作
- 关注：循环衔接是否平滑、节奏是否舒服、有没有突兀的位置漂移
- **静帧好看 ≠ 循环好看**：位置漂移通常只会在循环播放时暴露

### 第 4 步：拿给用户/维护者评审

3 种结果：

- **方向 OK，细节小修** → 保留评审基线，继续修当前候选或另存修订版
- **方向 OK 大体可以但要改某关键点** → 明确保留项，只改请求范围，再比较
- **方向不对** → 记录放弃原因，另存候选换方向

### 第 5 步：锁定（lock）

- 把当前 vN 复制到 `_locked-backups/<state>-vN-backup-YYYY-MM-DD.svg.html`
- 把当前 vN 复制到 `confirmed/states/<state>-<approach>-vN.svg.html`
- 标明旧候选是否未选或已被替代；需要归档时先处理重建依赖

### 第 6 步：写 spec

把这个状态的关键参数写进对应文档：

- 角色状态的 spec 写在角色项目的 `docs/states/<state>.md`，无论是否套 preset
- 通用经验可先记在角色项目中；本次任务已包含共享工具包维护时，再提炼到 `routes/svg/lessons/pitfalls.md` 或相应约定。普通角色修复不自动扩大为修改共享 skill

spec 应该包含：
- 使用的基线、来源及 preset（如有）
- 自定义参数（哪些数值改了，为什么）
- 关键技术点（用的 transform 还是 path morph 等）
- 锁定日期 + 锁定时用户/维护者的判断依据

### 第 7 步：同步进度表

如果项目有进度表，更新它：

- 状态从 ⬜ 改成 ✅
- 加锁定日期
- 加一行简评（突出贡献：节奏 / 几何 / 教训）

## 元教训（流程层面）

1. **v1 之前必须看参考**：先确认造型、拓扑和运动约束，再开始制作
2. **循环要覆盖多个完整周期**：不是“觉得差不多”，要看见最长的次级动作完整发生
3. **保留失败原因与来源链**：按需归档，移动前核查重建依赖
4. **改前先备份**：保留可回退版本，避免一次修改抹掉已通过的结果
5. **锁定要正式**：备份 + spec + 进度表 同步，不留尾巴
6. **spec 写"为什么"不只写"是什么"**：参数值后面加一句"因为 X"，未来才能判断要不要改

---

## 进度预期

制作时间取决于角色拓扑、动作段数、是否已有分层母版、目标运行时和反馈轮次。不要把示例天数或固定倍数当成通用排期；先用一个有代表性的状态验证工具链，再根据实际返工量更新剩余估算。
