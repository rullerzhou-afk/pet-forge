# 磨制流程：v1..vN → lock → spec

> 单个状态从"想做"到"锁定"的标准流程。

---

## 流程总览

```
[草稿]
   │
   ▼
[v1: 第一个方向]
   │
   ├─ 方向认可 ──▶ [保留评审基线，继续磨]
   │
   └─ 跑偏 ──▶ [记录原因，另存候选换方向]
                  │
                  ▼
                [v2: 新方向] → 同样的判断
                  │
                  ▼
                ... vN ...
                  │
                  ▼
              [lock]
                  │
                  ▼
              [备份 + 写 spec + 同步进度表]
```

---

## 关键概念

### 方向写进名字，版本号记评审轮次

- 方向写进文件或目录名：`<state>-<方向>-vN`。换方向就换名字、从 v1 开始，例如“探头方向”“球化方向”“凸起方向”各自是一条线。看名字就能数出试过几条路。
- 同一方向里，**给用户看过的每一版都另存递增版本号**，不覆盖被评审过的文件；用户可以直接说“就定 v8”。
- 还没给用户看的小修，在当前版本上改即可（改前照常备份），不要每修一处就开一个新版本号。

### 未选方向不删除

这是归档规则的唯一出处，其他文档只链接到这里：

- 未选方向放进 `_archive/<state>/`，或留在实验目录并在 README 标明“未选 / 已被替代”，两种都可以，但不删除；
- 搬移前检查构建脚本、素材引用和其他候选是否依赖原路径，搬移后验证能重建；
- 写一句放弃原因。

理由：

- 后续磨制可能想"绕回去看看那条路是不是真的死胡同"
- 跑偏的具体细节（哪一步翻车、为什么）是元教训源头，删了就丢了
- 人工评审 / AI 复盘时需要看历史，否则"为啥放弃这条路"无从查起

### 改之前先备份

**这条是硬规则**：改任何已经基本能看的动画文件之前，先保留一份可回退版本，不论有没有给用户看过。可以是带日期的副本、不可变快照目录或版本控制提交；要包含当时实际依赖的控制器和输入，不只留一张截图。

单文件备份示例（先确认目标名尚未使用，避免覆盖）：

```bash
cp idle-eye-follow-v1.svg.html idle-eye-follow-v1-backup-2026-05-02.svg.html
# 然后再改
```

理由：磨制经常"调着调着发现昨天那版本反而更好"，没备份就丢了。

## 单状态完整流程

### 第 1 步：草稿前准备（必做）

新状态开工前：

1. 看已有确认清单及相关状态，确定这次修改的基线和范围
2. 重读：
   - `routes/svg/conventions/svg-vs-canvas.md`（避免错选 Canvas）
   - `routes/svg/conventions/single-file.md`（自包含范式）
   - 需要套 preset 时才读对应预设；已有角色先保留其造型约定
3. 看公开案例或自己的历史状态里是否有类似动作

> 这一步看似繁琐，但很多跑偏都来自开工前没复查约束。

### 第 2 步：v1 起手

- 文件名：`<state>-<方向描述>-v1.svg.html`
- 从零起稿可复制 `templates/hello-idle.svg.html`，替换占位角色并保留有用的变量注释。
- 已有分层 SVG 时先核查图层、锚点、表情和控制器；从母版或已有确认动作的来源另存实验，保留造型真相源，不必重新套模板或 preset。
- 先分清请求是可保持的手动姿态、动态余动，还是完整表演；见 [rig-first.md](rig-first.md)。

### 第 3 步：按动作类型检查过程

可保持姿态检查停姿、慢拖、快拖和反向；一次性动作检查启动、全过程与目标姿态；只有声明为循环的动作才要求闭环。一次性动作在预览页里循环时跳回起点只是预览行为：不要自行补做回程，也不要声称已有回程。

头部或身体动作还要检查附近的毛发和配饰是否跟着动，规则见 [rig-first.md](rig-first.md) 的“毛发与配饰默认跟随”。

对循环动作，静帧不能代替播放检查：

- 浏览器开发者工具关掉，全屏播放足够多的完整周期，至少覆盖最长的眨眼、呼吸或次级动作
- 关注：循环衔接是否平滑、节奏是否舒服、有没有突兀的位置漂移
- **静帧好看 ≠ 循环好看**：位置漂移通常只会在循环播放时暴露

### 第 4 步：拿给用户/维护者评审

收到用户意见、动手改之前：

- **先对齐需求**：用户描述的部位不确定时，在截图上圈出你理解的位置；再复述这次要的是“可保持的姿态”还是“一段动画”。对齐后再做。
- **核对历次修正**：把用户在前几轮提过的设计修正列成清单，每轮出图或改稿前逐条核对。
- **用图说话**：视觉方向用文字说不清，或同一问题两轮没做对时，出参考图让用户挑，见 `shared/lessons.md` #12。

评审页要求：

- 默认用与角色主色反差大的舞台（浅色角色用深色），带深 / 浅 / 透明棋盘切换；
- 提供慢放（半速或更慢）和暂停拖动；修复类改动并排给出改前 / 改后对照，不只用文字描述；
- 新模块可单独开关，便于和已确认版对照；
- 交付时给出可直接打开的预览入口，并写明哪些部位仍然不动、哪些还没做。

拿给用户前先自己按同样方式看一遍：换稿或交接前后逐帧看，边缘放大 2–3 倍。数值检查通过的跳帧、色差和边缘污染，用户在慢放和反差背景下仍可能看出来。

3 种结果：

- **方向 OK，细节小修** → 另存下一个版本号再修，被评审的版本不覆盖
- **方向 OK 大体可以但要改某关键点** → 明确保留项，只改请求范围，再比较
- **方向不对** → 记录放弃原因，换方向名从 v1 开始

### 第 5 步：锁定（lock）

- 把当前 vN 复制到 `_locked-backups/<state>-vN-backup-YYYY-MM-DD.svg.html`
- 把当前 vN 复制到 `confirmed/states/<state>-<approach>-vN.svg.html`
- 旧候选按上文“未选方向不删除”处理
- 项目用版本控制时，用户认可后就提交一个检查点（agent 没有提交权限时，提醒用户提交）；不要攒到多个部件一起提交
- 部件认可后接回完整预览，和其他已认可动作一起看，再给用户看一次合体效果；合体方法见 [motion-composition.md](motion-composition.md)

### 第 6 步：写 spec

把这个状态的关键参数写进对应文档：

- 角色状态的 spec 写在角色项目的 `docs/states/<state>.md`，无论是否套 preset
- 通用经验可先记在角色项目中；本次任务已包含共享工具包维护时，再提炼到 `routes/svg/lessons/pitfalls.md` 或相应约定。普通角色修复不自动扩大为修改共享 skill

spec 应该包含：
- 使用的基线、来源及 preset（如有）
- 自定义参数（哪些数值改了，为什么）
- 关键技术点（用的 transform 还是 path morph 等）
- 锁定日期 + 锁定时用户/维护者的判断依据

### 第 7 步：同步进度表

如果项目有进度表，更新它：

- 状态从 ⬜ 改成 ✅
- 加锁定日期
- 加一行简评（突出贡献：节奏 / 几何 / 教训）

## 元教训（流程层面）

1. **v1 之前必须看参考**：先确认造型、拓扑和运动约束，再开始制作
2. **循环要覆盖多个完整周期**：不是“觉得差不多”，要看见最长的次级动作完整发生
3. **未选方向不删除**：归档或原位标记，移动前核查重建依赖
4. **改前先备份**：硬规则，保留可回退版本，避免一次修改抹掉已通过的结果
5. **锁定要正式**：备份 + 提交 + spec + 进度表 同步，不留尾巴
6. **spec 写"为什么"不只写"是什么"**：参数值后面加一句"因为 X"，未来才能判断要不要改

---

## 进度预期

制作时间取决于角色拓扑、动作段数、是否已有分层母版、目标运行时和反馈轮次。不要把示例天数或固定倍数当成通用排期；先用一个有代表性的状态验证工具链，再根据实际返工量更新剩余估算。
